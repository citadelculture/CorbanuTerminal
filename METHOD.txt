V2 change and historical limit
The first v1 run stopped after successful public acquisition because its guard
classified any target-directory entry as a product build output. Its target
inventory was not captured, so the historical file names and contents remain
unknown. Exact Cargo1.99.1 source at 5f94df4789f005f9a352888e8355ffc645b7ed0e
shows that fetch constructs RustcTargetData and caches rustc query output at
build_dir/.rustc_info.json; build_dir falls back to target_dir. This establishes
a metadata-only mechanism, not the uncaptured contents of that failed run.

V2 uses a separate /owned/acquisition-metadata-target for all acquisition and
qualification preflight commands, including full just fmt and offline cargo
metadata. It records the effective normalized CARGO_TARGET_DIR and incremental
setting on every phase. Bounded non-following inventories retain relative paths,
entry types, executable bits, file sizes and hashes before any acceptance check.
Limits are128entries,16MiB hashed content, depth4. Partial inventories remain
explicitly incomplete. The only permitted metadata file is a nonexecutable,
regular .rustc_info.json <=1MiB matching Cargo's exact cache structure; an empty
metadata target is also permitted. Any other file, directory, symlink, special
entry, malformed cache or compiled output refuses execution. No cache bytes
are exported. The metadata cache is hashed in the acquired-input handoff and
reverified before qualification, then independently checked after formatting
and offline preflight. Failure-path inventories survive refusal.

The separate /owned/target is inventoried empty before acquisition, after it,
on qualification entry, and immediately before the first compilation. It is
never deleted or cleared to manufacture freshness. Only after the last empty
target proof does the worker switch CARGO_TARGET_DIR to /owned/target for
ordinary compilation, clippy and four selected bodies. Metadata files are not
promoted into that target, and compiled output is never reused from acquisition.
The existing source, four bodies/five intents, containment, timeout, resource,
cleanup and normalization contracts are otherwise unchanged. This v2 branch
and workflow are a changed method, not a rerun of v1; no unchanged replay.

Runtime compartment and controls
The final worker uses that same exact image with network=none, read-only rootfs,
private PID/IPC/network namespaces, all capabilities dropped, no-new-privileges,
512 pids, two CPUs, 12GiB memory/no swap, owned writable public source/cache/target,
and a fresh owned HOME. There is no Docker socket, runner credential directory,
native credential bus or host profile mount. A synthetic host canary and live
host listener are deliberately outside all mounts. Its address is selected only
from the unique IPv4 default-route device; unrelated Docker bridge addresses do
not participate. Multiple default-route devices or addresses stop the run.
Controller proves the actual
listener responds before and after the campaign; actual worker and child must
fail reaching it and link-local metadata, while IPv4 and IPv6 loopback round
trips and owned writes succeed. Worker and child must have distinct host PID/net
namespace identities, only lo, and no direct or /proc-host-root canary visibility.
The exact Docker configuration is independently inspected before start.

HOME=/owned/home is the dedicated container identity from image creation, never
an operator HOME reassignment. Any inherited live profile alias stops dispatch.
Every inherited CODEX sandbox marker is preserved byte-for-byte in both workers;

test itself creates and removes its disposable CODEX_HOME and scratch. The host
container identity is not the owner's host test environment.

debug assertions remain true. The unchanged ordinary wrapper builds all bins
